## 1. Each list

### A. Social tasks

- **Generated by** `buildSocialTasks(eventType, hostProfile, outfitPieces, context)` (EGS:157). It is a static template, not AI:
  - `SOCIAL_TASK_TEMPLATES` by event type (EGS:26-83): invite, brand_deal, guest, upgrade, with `default` = invite;
  - plus `PLATFORM_TASKS` for the host's platform (EGS:91-124);
  - plus `CATEGORY_TASKS` for the host's content category (EGS:129-153).
  - Descriptions are then rewritten with outfit pieces, host, venue, guests and dress code (EGS:178-222). The list is sorted before → during → after (EGS:249-250).
  - The PNG is rendered by `renderSocialChecklist` (`src/services/socialChecklistService.js:51`).
- **When it is generated:**
  - At event creation from the calendar, `spawnEventsFromCalendar` (`src/services/eventAutomationService.js:734-764`). The event type there is only `invite`, `guest` or `upgrade` (`:737`).
  - At event creation from a profile, `POST /world/:showId/events/from-profile` (WE:2475). The inputs are hard-coded to `'invite'` and `instagram` (WE:2716-2720).
  - On click, `POST /world/:showId/events/:eventId/generate-social-checklist` (WE:3206):
    - WorldAdmin's "Regenerate Social Tasks" button sends `force: true` (`WorldAdmin.jsx:4309`);
    - Mark Ready also calls it (`WorldAdmin.jsx:4430`);
    - it rebuilds only when forced or when the list is empty (`socialChecklistService.js:254`).
  - On click, `POST .../generate-overlay/social` (WE:3458). It builds from `(event_type, hostProfile, outfitPieces)` with no context, when the event has no tasks yet (WE:3514-3528).
  - At episode generation (Start Episode), `generateEpisodeFromEvent`, reached from `generate-episode` (WE:2161), `generate-episode-from-many` (WE:2262) and `regenerate-episode` (WE:2376). It copies the event's tasks, or builds them if there are none (EGS:855-882).
- **Inputs:**
  - used: `event_type`; the host profile's `platform` and `content_category`; `outfit_pieces`; `event.name`; host name, handle and `host_brand`; `venue_name`; `dress_code`; guest names;
  - not used: deliverables, `requirements`, `restrictions`, `is_paid`, `payment_amount`, beats, character state.
- **Stored in two places:**
  - on the event, `world_events.canon_consequences.automation.social_tasks`, written by `socialChecklistService.js:338-345` and by approve-overlay (WE:3672);
  - on the episode, `episode_todo_lists.social_tasks`, JSONB, with the comment `'Social media content tasks: [{slot, label, description, required, completed, platform, timing}]'` (`src/migrations/20260712000000-wardrobe-pricing-episode-financials-social-tasks.js:48-53`). `episode_todo_lists` has no Sequelize model; every access is raw SQL.
  - The PNG assets use two roles: `UI.OVERLAY.SOCIAL_CHECKLIST` (`socialChecklistService.js:315`) and `UI.OVERLAY.SOCIAL_TASKS` (WE:3531).
- **Who can edit:** every route is `requireAuth` only.
  - Toggle `completed`: `POST /api/v1/episodes/:episodeId/todo/complete-social/:slot` (TLR:288), from the Run Sheet row click (`EpisodeTodoPage.jsx:95-101, 236`).
  - Edit labels and descriptions: the "Edit Tasks" tab of `OverlayApprovalPanel` (`:259-292`), then re-render and approve. Approve writes the **event** copy only (WE:3669-3673). The episode copy is upserted only for the wardrobe role (WE:3681).
  - Regenerate the event copy: the "Regenerate Social Tasks" button. The episode copy is rewritten only by regenerating the episode.
  - There is no route that adds or deletes a single task.
- **Readers:**
  - **Episode completion.** `completeEpisode` reads `episode_todo_lists.social_tasks` (ECS:222). `computeSocialTaskBonuses` (ECS:34-72) turns `completed` and `required` into reputation, influence and stress deltas. They are returned as `social_tasks` (ECS:737).
  - **Money.** `finalizeEpisodeFinancials` reads the episode copy (FTS:441), falling back to the event copy when that is empty (FTS:455). `calculateSocialTaskRewards` pays completed tasks only (FTS:308-328), at required 25 or optional 10 (FTS:29-33), times the timing multiplier: before 1.0, during 1.2, after 0.8 (FTS:35-39). The rows are booked as `social_task_reward`. The financial forecast estimates the same rewards from the event copy (WE:3021-3022).
  - **Script.** `loadScriptContext` reads the episode copy (`episodeScriptWriterService.js:269`) and writes the prompt directive "SCRIPT DIRECTIVE: Lala must reference creating this content — filming stories, going live, angling her phone. The content tasks are part of the episode action." (`:558`). `groundedScriptGeneratorService` and `scriptSkeletonGenerator` do not read them.
  - **Distribution.** `distributionService.js:103-109, 165-166, 296` reads "Social Tasks: X/Y completed".
  - **Overlay suggestions.** `suggestOverlaysForEvent` offers `social_tasks` when the event has any (`uiOverlayService.js:150-151`).
  - **Summary cards.** The EpisodeAssetsTab card (`:66-69, 119-124`), and E's `social_checklist` item, which checks only that a `SOCIAL_CHECKLIST` asset exists (`EpisodeProductionChecklist.jsx:252-256`).

### B. Episode To-Do (the wardrobe list)

- **Generated by one of three code paths:**
  1. **AI.** `generateTasks(event)` (TLS:52), model `claude-haiku-4-5-20251001` (TLS:108). The prompt opens "You are writing Lala's wardrobe shopping list — a dreamy, specific to-do list she makes while getting ready for an event." (TLS:58). It asks for 7 tasks, one per slot in `SLOTS` (TLS:40-48). The fallbacks are `VIBE_FALLBACKS` (TLS:128-144).
  2. **Static.** Episode generation writes 5 fixed tasks, e.g. `` label: `Outfit for ${event.name}` `` (EGS:885-891).
  3. **From picked pieces.** `generate-overlay/wardrobe` maps `outfit_pieces` to tasks with `completed: !!piece.is_owned` (WE:3487-3504). It falls back to `generateTasks` when no pieces are picked.
- **When it is generated:**
  - at episode generation (EGS:899-913);
  - on click, `POST /api/v1/episodes/:episodeId/todo/generate` (TLR:17), from the "Generate Wardrobe Shopping List" and "Regenerate" buttons (`EpisodeTodoList.jsx:127-135, 264-271`);
  - on approving a wardrobe overlay, which overwrites `episode_todo_lists.tasks` from the asset's `metadata.tasks` when the event is linked to an episode (WE:3680-3701);
  - `POST /world/:showId/events/:eventId/generate-lists` (WE:4335) can also generate it, but no caller of that route exists in `frontend/src`.
- **Inputs:**
  - AI path: `event.name`, `theme`, `mood`, `dress_code`, `dress_code_keywords`, `location_hint`, `prestige`, `narrative_stakes` (TLS:53-77);
  - static path: `event.name` and `dress_code`;
  - overlay path: `outfit_pieces`;
  - none of the three uses deliverables, terms, beats or character state.
- **Stored in:**
  - `episode_todo_lists` (`src/migrations/20260705000000-create-episode-todo-lists.js`): one row per episode (`episode_id` unique, `:19-25`), with `tasks` JSONB `'Array of task objects, one per wardrobe slot'` (`:37-42`) and `status` `draft | generated | locked` (`:59-63`);
  - on the event, `automation.wardrobe_tasks` (WE:3668);
  - as assets with the role `UI.OVERLAY.WARDROBE_LIST` (TLS:465).
- **Who can edit:** every route is `requireAuth` only.
  - Include or exclude: `POST /todo/save-selection` (TLR:130). It replaces the whole array; the UI only flips `included` (`EpisodeTodoList.jsx:71-80`).
  - Lock and unlock: `POST /todo/lock` (TLR:151) and `/todo/unlock` (TLR:271).
  - Toggle `completed`: `POST /todo/complete/:slot` (TLR:75), from the Run Sheet (`EpisodeTodoPage.jsx:84-93`). **`getTodoList` recomputes `completed` on every read** from the wardrobe slots the episode has filled: `completed: filledSlots.has(t.slot)` (TLS:576-582). A manual toggle is therefore replaced on the next GET.
  - Edit labels: the overlay approval panel, through the wardrobe approve path.
- **Readers:**
  - **The timeline.** Locking re-renders the PNG and places it on the first scene by `scene_number` with `placeOverlayOnFirstScene(... properties: { kind: 'wardrobe_checklist', source: 'todo-lock' })` (TLR:240-247).
  - **Overlay suggestions.** `wardrobe_list` is offered when outfit pieces exist or prestige ≥ 4 (`uiOverlayService.js:141-142`).
  - **UI.** Wardrobe gameplay progress (`EpisodeWardrobeGameplay.jsx:317-341`), the EpisodeAssetsTab card, and the Run Sheet.
  - **Not read by** completion, money, script or distribution. Each of them selects only `social_tasks`.

## 2. The Career Checklist claim

> "The Career Checklist result is kept only in component state and never
> saved or reloaded."

**The claim is CONFIRMED for the task data.**
- **Not stored:**
  - `generateCareerList` writes no row to `episode_todo_lists` (TLS:674-717).
  - The tasks go only into `const [careerList, setCareerList] = useState(null)` (`EpisodeTodoList.jsx:20`), set only from the generate response (`:63`).
- **Not reloaded:**
  - On mount the component GETs `/todo` (`:29-43`), which returns `episode_todo_lists` data through `getTodoList` (TLS:551-595). That data holds no career tasks.
  - So after a reload `careerList` is null, and the tab again offers "Generate Career Checklist" (`:202-218`).

**The claim is CORRECTED on "never saved".**
- **What is saved:** each generation uploads a PNG and inserts an `assets` row with `asset_type: 'TODO_LIST'`, `asset_role: 'UI.OVERLAY.CAREER_LIST'` and `approval_status: 'approved'` (TLS:691-705).
  - Its metadata keeps `task_count` but not the tasks (TLS:706-713). The task text survives only as pixels in the PNG.
  - Each Regenerate adds another row; nothing removes the older ones.
- **What reads it:** EpisodeAssetsTab reads that row's existence (`EpisodeAssetsTab.jsx:77, 126-129`).
- **What still disappears on reload:** the component does not reload its own asset, so "Preview Overlay" is gone after a reload (`EpisodeTodoList.jsx:147`).

## 4. Beats and the phone

**No list places its items at a beat today.**
- No item in any list has a `beat`, `beat_number` or `surface` field.
- Social tasks carry `timing` (before, during, after), used only to group the rendered checklist (`socialChecklistService.js:43-47`) and the script prompt.
- Wardrobe `slot` is a clothing category.

**What the beat model says about a to-do list:**
- Canonical beat 9, "Reminder/Deadline", has `screen_action: 'TODO_LIST'`, `surface: "Lala's Phone"` and `diegetic: true`, with the comment "Evoni's ruling: the to-do list is Lala's; she sees it on her phone." (`src/constants/canonicalBeats.js:226-242`).
- Beat 12, "Deliverable Creation", is `CONTENT_CREATE` on Lala's Phone (`:281-295`).
- The script writer and the grounded generator map beat 9 to `ui: 'TODO_LIST'` (`episodeScriptWriterService.js:60`; `groundedScriptGeneratorService.js:48`).
- The skeleton instead writes `ToDoListOverlay` at `## BEAT: STAKES_INTENTION` (`scriptSkeletonGenerator.js:136-140`).
- The only thing that places a list on the timeline is the wardrobe lock, which puts it on the **first scene** (TLR:240-247), not at beat 9.

**How the phone overlays pick a list: they don't.**
- `ScreenContentRenderer` has no task, checklist or todo content type.
- No phone code reads a task list (`PhoneHub.jsx`, `UIOverlaysTab.jsx`, `frontend/src/lib/phoneRuntime.js`, `src/services/phoneRuntime.js`, `phoneContextBuilder.js`, `phoneScreenRenderer.js`).
- The phone's asset lists read only `asset_type = 'UI_OVERLAY'` (`uiOverlayRoutes.js:43`; `phoneContextBuilder.js:66`). So the wardrobe and career PNGs (`TODO_LIST`) and the social checklist PNG do not reach them.
- The overlay "picker" is the event's `required_ui_overlays`, chosen from `suggestOverlaysForEvent` (`uiOverlayService.js:141-151`), which suggests `wardrobe_list`, `career_list` and `social_tasks` by event type and prestige.
- `autoPlaceRequiredOverlays` places those it can match by `metadata.overlay_type` (`timelinePlacementService.js:128-187`).
- `iconCueGeneratorService.js:268-279` places a `UI.ICON.TODO_LIST` icon, not the list, on a scene whose name mentions "to-do", "todo" or "task".
- CANNOT-TELL, from code alone, whether any social or wardrobe PNG carries `metadata.overlay_type`, and so whether `autoPlaceRequiredOverlays` ever places one.

## 6. Also found in the read (MEASURED, not ruled)

- **Two copies of social tasks drift.**
  - Edits, approval and regeneration after Start Episode change only the event copy (WE:3669-3673; `socialChecklistService.js:338-345`).
  - Completion, money, script and distribution read the episode copy first (ECS:222; FTS:441; `episodeScriptWriterService.js:269`; `distributionService.js:104`).
- **Regenerating an episode resets both lists,** `completed` flags included: `ON CONFLICT (episode_id) DO UPDATE SET tasks = EXCLUDED.tasks, social_tasks = EXCLUDED.social_tasks` (EGS:901-902).
- **B's `completed` is derived on read** from the episode's filled wardrobe slots (TLS:576-582), so `POST /todo/complete/:slot` does not survive a reload for B.
- **A stale comment:** "world_events has no deleted_at column" (TLS:440). The canon capture has `world_events | deleted_at` (`docs/audit/EvidenceNote_Canon_Schema_Capture_2026-09-17.txt:2638`), and `generateCareerList`'s event query (TLS:677-680) does not filter on it.
- **A render detail:** the career row divider uses the wardrobe `tasks.length` (`EpisodeTodoList.jsx:312`).
- **No routes check ownership:** all task-list routes use `requireAuth` only, with no show or episode ownership check (e.g. TLR:17, 38, 75, 288).
- **`financial_summary` may count the whole closet:** it is computed by `calculateFinancials(event, options.wardrobeItems)` (EGS:894). `generate-episode` passes every wardrobe row of the show (WE:2189-2202), so its `outfit_cost` can sum the whole closet (EGS:299-302). This is a reading of the code, not checked against data.
