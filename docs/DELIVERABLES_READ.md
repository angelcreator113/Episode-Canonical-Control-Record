# Deliverables — a read, not a ruling

## Status of this document

**Read-only research, not a decision.** This is not filed under `docs/audit/` and rules nothing. It
exists so Evoni can rule on what deliverables are, where they live, and whether delivering them
matters, with the whole picture in front of her. Nothing here changes code, runs a query, proposes a
schema, or writes a migration.

Every claim is **MEASURED** (a repository read anyone can repeat, with a file:line) unless it is
marked **INFERRED**. Nothing is RULED.

Basis for the file:line citations below: `origin/main` at
`4862ff8115102e7a69780a32d7d2c64708dc5e51` (2026-09-24). Line numbers drift; the function and field
names are the stable part.

It builds on `docs/EVENT_EPISODE_FLOW.md` §8(s), "Deliverables and the social package" (Task
#1773). That section separates **Lala's deliverables** (canon asks of her by a brand or organizer)
from **the show's social package** (Prime Studios' own distribution). This read cites §8(s) and does
not restate it.

Task: #1806.

## 0. The answer that shapes the rest

**Nothing that changes brand trust, or any brand or relationship score, reads a deliverable, a
delivery record, or a task completion.** The loop "a brand asks, Lala delivers, the relationship
moves" has no mechanism today.

- **What moves brand trust** (`character_state.brand_trust`), all through `completeEpisode`
  (`src/services/episodeCompletionService.js`):
  - the evaluation tier's fixed deltas (`computeStatDeltas`, `src/utils/evaluationFormula.js:297`
    onward: slay gives +1, fail gives −1);
  - wearing two or more identifiable brands, and wearing the host's brand
    (`computeWardrobeBonuses`, `episodeCompletionService.js:81-86`);
  - creator-authored `event.rewards.brand_trust`, applied on slay or pass
    (`episodeCompletionService.js:280-289`);
  - a manual admin edit (`src/routes/evaluation.js`, `POST /characters/:key/state/update`).

  None of these reads an ask or a delivery.
- **The one delivery-like input that does count:** the `completed` flag on social tasks in
  `episode_todo_lists.social_tasks`. `computeSocialTaskBonuses` (`episodeCompletionService.js:32-56`)
  turns the completion rate into reputation, influence and stress changes, and
  `calculateSocialTaskRewards` (`src/services/financialTransactionService.js:286-307`) pays coins per
  completed task. **It never touches brand trust**, and the tasks are generated by event type, not
  supplied by a brand (§1.3).
- **A misleadingly named bonus.** The "Content delivery bonus" (`financialTransactionService.js:
  470-479`) pays 10% of the event payment on any paid `brand_deal` event. It checks no delivery.
- **Brand-level scores do not exist.** There is no brand-trust or brand-relationship column or model.
  `LalaverseBrand` has only `partnership_status`, set once on create
  (`src/routes/wardrobeBrands.js`). `getBrandRelationships` (`wardrobeIntelligenceService.js`) is
  computed on read from outfit wears, and writes nothing.
- **Relationship-to-Lala scores on Feed profiles do not read delivery either.**
  - `syncAfterEvent` (`src/services/characterSyncService.js:97-197`) moves the host's
    `lala_relevance_score` by event prestige, and `current_state` by event history and tier.
  - Advancing an opportunity to booked or completed sets Lala's own profile to "peaking" when
    prestige is 7 or more (`src/routes/opportunityRoutes.js:190-196`).
- **Career goals do not read delivery.** `onOpportunityAdvanced` (`src/services/careerPipelineService.js`)
  increments goals from `payment_amount`, `prestige`, `opportunity_type` and `social_boost` only.
  For example, a `brand_trust` goal gains on any completed `brand_deal` (around line 71).
- **Script stat tags are never applied.** `[STAT_CHANGE: …]` tags in scripts are parsed
  (`src/utils/scriptBeatParser.js:137`), but no code applies them.

**INFERRED:** an opportunity marked completed moves career goals the same way whether or not
anything was delivered. Only the social-task completion rate distinguishes a diligent episode from a
careless one, and only through reputation, influence, stress and coins.

## 1. Where the ask is stored

### 1.1 `Opportunity.deliverables`
- **Declared:** JSONB, default `[]`, comment `[{type, description, due_date, completed}]`
  (`src/models/Opportunity.js:62`).
- **Its only writer:** `POST /opportunities/:showId` (`src/routes/opportunityRoutes.js`).
  - When the body has no deliverables, it fills them from `TYPE_DEFAULTS` (`:41-51`) as
    `{ description, completed: false }` (`:96-97`). The stored shape has no `type` and no
    `due_date`, whatever the model comment says.
  - The defaults are short strings per opportunity type. For example, brand_deal gets "Sponsored
    content", "Story mentions" and "Engagement targets". Panel, pr_gifting and casting_call have no
    defaults.
  - Neither frontend form sends deliverables (`WorldAdmin.jsx` quick form and full form), so every
    stored list is a type default.
- **A dormant writer:** the generic `PUT /opportunities/:showId/:id` (`opportunityRoutes.js:134-151`)
  runs `opp.update(body)` and could write the field. No frontend caller uses it.
- **Other opportunity creators write none:** `feedEventPipelineService.js` (around line 300),
  `careerPipelineService.spawnUnlockOpportunities` and
  `characterSyncService.generatePostEventOpportunities`.
- **Readers: none.** No backend code reads the field by name. No frontend renders it; the WorldAdmin
  opportunity card shows name, status, type, brand, payment and stakes. The script writer loads
  opportunities with an attribute list that excludes it (`episodeScriptWriterService.js:200-201`).

### 1.2 `Opportunity.content_requirements`
- **Declared:** JSONB, default `[]`, comment `[{platform, post_type, caption_approval,
  usage_rights}]` (`Opportunity.js:64`).
- **No writer and no reader** anywhere beyond the model and its migration
  (`20260717000000-create-opportunities-table.js:32`).
- Two of its neighbours are also never written: `exclusivity` (TEXT, `:65`) and `content_generated`
  ("posts from this opp", `:91`).

### 1.3 Neither reaches the event
There are two opportunity-to-event paths, and neither copies deliverables or
`content_requirements`:
- **`scheduleOpportunityAsEvent`** (`src/services/feedEventPipelineService.js`, around line 372). This
  is the one-click path called from WorldAdmin. It carries over `wardrobe_brief.dress_code` and
  `career_milestone` only.
- **`convertOpportunityToEvent`** (`src/services/careerPipelineService.js:179-237`). It copies the
  whole `wardrobe_brief` into `automation`. No frontend caller was found.

`WorldEvent` has no deliverables column (§8(s) item 4, confirmed at this basis).

### 1.4 Other fields that hold something like an ask
- **`canon_consequences.automation.social_tasks`** (event), and
  **`episode_todo_lists.social_tasks`** (episode). Built by `buildSocialTasks` from
  `SOCIAL_TASK_TEMPLATES`, `PLATFORM_TASKS` and `CATEGORY_TASKS` (`src/services/episodeGeneratorService.js`)
  by event type, platform and category.
  - They read as **Lala's own in-story posting to-do list** (GRWM, arrival, thank the host), not as
    the show's social package in §8(s)'s sense, and not as a brand's contract.
  - Only the brand_deal template reads like a sponsor ask ("Sponsored Post 1 — must follow brief"),
    and even that comes from the event type, not from anything the brand supplied.
  - **INFERRED:** these are the nearest thing to deliverables that the game actually plays.
- **`dress_code` and `dress_code_keywords`** (event), and **`Opportunity.wardrobe_brief`**
  (`{dress_code, brands_required, style_direction, provided_pieces}`). A wardrobe ask:
  `brands_required` is the only brand-supplied constraint on Lala in the data.
- **`requirements`** (event). See §4: in practice these are stat thresholds, not asks.
- **`fail_consequence` and `success_unlock`** (event). Outcomes, not asks. `success_unlock` bumps
  career goals on slay or pass (`episodeCompletionService.js:547`).
- **The career task list.** `generateCareerTasks` (`src/services/todoListService.js:606-669`)
  prompts an AI for "deliverables… brand obligations", but `generateCareerList` only renders a PNG
  and an Asset. The tasks are not stored in any table.
- **Episode sponsor fields** (`CreateEpisode.jsx`: `deliverables`, `sponsor_expectations`,
  `collab_deliverables`). These are about the show's real-world sponsor, not Lala, and have no
  matching columns. They are out of scope, and are named here because they share the word.

## 2. Where delivery is stored

**For a brand's ask, nowhere.**
- `Opportunity.deliverables[].completed` is written `false` on create and **never set to true** by
  any code. The only possible writer is the unused generic PUT.
- An opportunity's `status → completed` is a different thing. It is set by hand through
  `POST …/advance` (`opportunityRoutes.js:164-187`), or by `onEpisodeCompleted`
  (`careerPipelineService.js:287-291`, reachable only through a route with no frontend caller). It
  does not look at deliverables.
- No `delivered` column or field exists anywhere in `src/`.

**For Lala's generated social tasks, one record, set only by hand:**
- `episode_todo_lists.social_tasks[].completed` is seeded `false` at episode generation
  (`episodeGeneratorService.js`, around lines 761-819).
- It is set by the two routes in `src/routes/todoListRoutes.js`: `POST
  /episodes/:episodeId/todo/complete-social/:slot` (around lines 288-310) and `…/todo/complete/:slot`
  (around lines 75-111). Both are called from `EpisodeTodoPage.jsx`, the only UI that checks tasks
  off.
- Nothing sets it automatically. Playthrough completion does not touch it.
- It is **read automatically** only when the episode completes (§0), and
  `evaluation_json.social_task_bonuses` records the counts (`episodeCompletionService.js`, around
  lines 428-452).
- **After the episode is accepted, toggling does nothing.** `completeEpisode` returns
  `already_completed`.

**Adjacent, not delivery:**
- The event's own `automation.social_tasks[].completed` is always `false`; nothing toggles it.
- The wardrobe `tasks[].completed` is overwritten on read by `getTodoList`
  (`todoListService.js:576-582`) from the outfit actually chosen, so a manual toggle is masked.

## 3. Which reader turns delivery into relationship or career change

This is answered in §0 with citations. In short:

| Writer | Reads a deliverable? | Reads a task completion? | Changes |
|---|---|---|---|
| `completeEpisode` → `computeStatDeltas` | No | No | All five stats, by tier |
| `completeEpisode` → `computeSocialTaskBonuses` | No | **Yes** | Reputation, influence, stress |
| `completeEpisode` → `computeWardrobeBonuses` | No | No | Brand trust (brands worn), stress, reputation |
| `completeEpisode` → `event.rewards` | No | No | Reputation, brand trust, influence (authored) |
| `finalizeEpisodeFinancials` | No | **Yes** | Coins |
| `syncAfterEvent` | No | No | Profile relevance, state |
| `/advance` "peaking" | No | No | Lala's profile state |
| `onOpportunityAdvanced` | No | No | Career goals |
| Manual state edit | No | No | Any stat |

**No writer reads `Opportunity.deliverables`, `content_requirements` or `WorldEvent.requirements`
as a delivery signal.**

## 4. What `requirements` means

- **Declared:** `WorldEvent.requirements`, JSONB, default `{}` (`src/models/WorldEvent.js:239-243`).
  The migration comment shows `{"reputation_min":5,"brand_trust_min":4,"portfolio_min":10}`
  (`20260219000004-world-events-career-fields.js`). No code writes or reads `portfolio_min`.
- **Writers.**
  - The event create route, the PUT (`requirements` is in `allowedFields`), and the bulk seed all
    store whatever JSON they are sent (`src/routes/worldEvents.js`).
  - The only UI writer is the old editor (`WorldAdmin.jsx`). Its `EMPTY_EVENT` default is
    `{ reputation_min: 0, brand_trust_min: 0, coins_min: 0 }` (around line 147). Its section is
    headed **"REQUIREMENTS — gates that dock score when unmet"** (around line 2667), with inputs for
    those three keys.
  - Every automated creation path leaves it `{}`.
  - **Keys actually written:** `reputation_min`, `brand_trust_min` and `coins_min`, all integers.
- **Its one real reader** is the next-event suggester (`src/routes/careerGoals.js:620-628`). If
  Lala's stats are below any minimum, the event's suggestion score drops by 5, it is flagged
  "requirements not met", and it is still returned. **It is a soft gate on a suggestion,** not on
  participation. Nothing in episode generation, Start Episode, evaluation or difficulty checks it.
- **Where it is shown.** The Event Package (`frontend/src/pages/EventPackagePage.jsx`, around line
  1140) has a section headed exactly **"Style & Deliverables"**. It shows two things:
  - "Outfit": a count of chosen pieces;
  - "Requirements": each key and value as written, for example "Reputation Min: 0", or "None set".

  **Nothing under that heading is a deliverable.** The "Deliverables" half of the heading has no
  data behind it. The code's own comments agree: `eventReadinessSections.js`, around line 120,
  reserves a section "once they have a home"; the test's own comment says "nothing real stores
  deliverables yet".
- **A copy nothing reads.** `episodeGeneratorService` copies `requirements` into the brief's
  `event_metadata.requirements` (around line 649), and no code reads that copy.
- **Its keys are shared with wardrobe fields.** `Wardrobe.unlock_requirement` and
  `reputation_required` use the same `*_min` stat-threshold vocabulary.

**So today `requirements` means entry thresholds on Lala's stats**, used to rank suggestions and
shown under a Deliverables heading. **INFERRED:** because it is free-form JSON accepted by every
write route, and sits under that heading, it is the likeliest place for a deliverable to be written
by hand if nothing else is decided. That is the "second home" risk.

## 5. Requirements, deliverables and restrictions: a sorting, for Evoni to rule on

The three categories are a proposal, not a ruling:
- **Requirements:** what Lala must do or have in order to participate.
- **Deliverables:** what she must produce.
- **Restrictions:** what she must not do.

| Field (where) | Sorted as | Why |
|---|---|---|
| `WorldEvent.requirements` (`reputation_min`, `brand_trust_min`, `coins_min`) | **Requirements** | Thresholds on Lala's state to take part. Today they only rank suggestions. |
| `Opportunity.deliverables` (type-default strings) | **Deliverables** | Things she produces: sponsored content, story mentions, walking the show. Includes items that are restrictions ("Exclusivity period", "Exclusivity compliance"). |
| `Opportunity.content_requirements` (`platform, post_type, caption_approval, usage_rights`) | **Deliverables**, with restriction terms | `platform`/`post_type` describe the output; `caption_approval`/`usage_rights` are conditions on it. Never written. |
| `Opportunity.exclusivity` | **Restrictions** | Not working with competitors. Never written. |
| `Opportunity.wardrobe_brief` (`brands_required`, `dress_code`, `provided_pieces`, `style_direction`) | **Requirements** (to appear) | A condition of taking part. `brands_required` edges toward a deliverable (wear and show the brand). |
| `dress_code` / `dress_code_keywords` (event) | **Requirements** | To attend. |
| `automation.social_tasks` / `episode_todo_lists.social_tasks` | **Deliverables**, of Lala's own making | Things she produces, but chosen by the game from event type, not asked by a brand, except the brand_deal template's wording. |
| `fail_consequence`, `success_unlock` | **None of these** | Outcomes. |
| `rewards` | **None of these** | What the event pays out. |
| Episode sponsor fields (`CreateEpisode.jsx`) | **None of these** | About the show's sponsor, not Lala (§8(s) item 2's side). |

**Where each category could live**, stated as options, not a design:
- **Requirements** already have a home in `WorldEvent.requirements`. The question is whether to
  widen it beyond stat thresholds (dress code, invitation, brands worn) or keep it to thresholds.
- **Deliverables** have a real structure only in `Opportunity.deliverables`, which never reaches
  the event. On the event, the only candidates are `requirements`, which would become a second
  home, and social tasks, which are generated rather than asked.
- **Restrictions** have only `Opportunity.exclusivity`, which is never written, and deliverable
  strings that are really restrictions.

**If nothing is decided,** `requirements` is the field most likely to become a second home for
deliverables, because it is free-form, writable everywhere, and already sits under a "Deliverables"
heading. The next most likely is `canon_consequences.automation`, which already carries
`wardrobe_brief` from one conversion path.

## 6. Deliverable load versus difficulty

- **How difficulty is computed.** The only formula is `calcEventDifficulty`
  (`frontend/src/utils/eventReadiness.js:86-94`), a weighted sum:
  - prestige ×0.35;
  - strictness ×0.30;
  - deadline weight ×0.20;
  - dress-code keyword count ×0.5 ×0.15.

  It is clamped to 1–10. `eventDifficultyLabel` names the bands. `projectEventDifficulty`
  (`frontend/src/utils/eventStakes.js:95-111`) wraps it for the Event Package's projected "Challenge"
  chip, and reports missing inputs instead of defaulting them. That follows
  `docs/audit/F-Stats-1_EventDifficulty_ProjectedVsCanonical_Decision_2026-09-24.md`: projected is
  for planning only, canonical uses only accepted values, and the keyword count is to be
  reassessed.
- **The backend has no difficulty score.** It snapshots the raw inputs into the brief
  (`episodeGeneratorService.js`, around lines 640-644). Evaluation reads the raw inputs, not the
  score.
- **A small anomaly:** a deadline of `none` weighs the same as `medium`, because its weight of 0
  falls through `|| 2`.
- **Nothing that Lala must produce feeds difficulty.** No input reads deliverables, social tasks,
  `content_requirements` or `requirements`.
- **No workload or load measure exists.** The nearest numbers are social-task counts and completion
  rates, used *after* the episode for stats and coins (§0), in the script prompt
  (`episodeScriptWriterService.js`, around lines 549-554), and in the distribution prompt
  (`distributionService.js`).

**Is deliverable load separable from difficulty?** Measured: yes, today they share no input.
Difficulty is about the room (prestige, strictness, deadline, dress code); load would be about what
she must produce. A gala can be hard with light deliverables; a brand activation easy with heavy
ones.

**What a separate measure would need as input** (not a design):
- a stored list of what Lala must produce for this event, which does not exist on the event today
  (§1.3);
- for each item, something countable, such as the number of posts or appearances, and when it is
  due;
- optionally, which items are required and which optional, as social tasks already carry.

Without the first, any load measure could only count generated social tasks, which measure the
game's template, not a brand's ask.

## 7. Open questions for Evoni

1. **Should delivering move anything?**
   - (a) Yes, brand trust: a brand's ask met or missed changes trust with Lala, and with that brand if
     brand-level trust is ever added.
   - (b) Yes, but only through social tasks, as today: reputation, influence, stress and coins.
   - (c) Not yet: record delivery first, and decide consequences later.

   The evidence forces one point: under (a), there is no delivery record to read today (§2), so a
   record comes first whatever else is chosen.
2. **Where do an event's deliverables live?**
   - (a) Carried over from `Opportunity.deliverables` when an opportunity becomes an event.
   - (b) On the event itself, set in the Event Package.
   - (c) Both: the opportunity's list seeds the event's.

   Events not created from an opportunity (from-profile, calendar, manual) have no source for (a).
3. **What is `requirements`?**
   - (a) Entry thresholds only, as today, with the Event Package heading changed so it stops saying
     "Deliverables".
   - (b) Widened to every participation condition (dress code, invitation, brands worn).
   - (c) Retired in favour of whatever holds requirements after question 5.
4. **Are social tasks Lala's deliverables, or something else?**
   - (a) They are her deliverables, and brand asks should be written into them.
   - (b) They stay her own in-story posting plan, separate from what a brand asks.
   - (c) Brand-supplied tasks join them, marked by source.
5. **Requirements, deliverables and restrictions:** are these the three categories, and does each
   get its own home? §5 sorts every field found. `Opportunity.exclusivity` and
   `content_requirements` have never been written, so they can be adopted or dropped without a data
   question.
6. **Deliverable load:** a measure separate from difficulty, to show in planning; or no measure until
   deliverables have a home (§6's inputs). No recommendation: the evidence only says a measure has
   nothing to count yet.
7. **Two misleading labels found on the way.** The Event Package's "Style & Deliverables" heading
   shows no deliverables, and the "Content delivery bonus" checks no delivery. Both could be renamed
   now, independent of the rest.

  while the career-goal sync reads `'lala'` (`src/routes/careerGoals.js`, around lines 381-384 and

  `completeEpisode` does not call it.
- **`syncAfterEvent` runs too early for tiers.** It runs at episode *generation*
  (`episodeGeneratorService.js`, around line 914), before evaluation, so its tier-based state change
  normally sees no tier.
- **A stale comment.** `WorldAdmin.jsx`'s comment on `EMPTY_EVENT.requirements` cites
  `careerGoals.js:655-656`; the code is now at 620-628.
